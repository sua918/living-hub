# 개발 규칙

## 1. 환경

권장 기본:

- Java 21
- Gradle Wrapper
- PostgreSQL
- Docker Compose는 로컬 DB 재현에만 선택적으로 사용
- 환경별 Spring Profile

버전은 빌드와 Wrapper 파일에 고정한다.
개발자 PC에 설치된 전역 Gradle을 기준으로 삼지 않는다.

## 2. 설정

```text
application.yml
application-local.yml
application-test.yml
application-prod.yml
```

규칙:

- 공통 안전 설정만 기본 파일에 둔다.
- 비밀값은 환경 변수로 주입한다.
- 운영 profile을 기본값으로 자동 활성화하지 않는다.
- 테스트는 운영 DB나 외부 서비스에 연결되지 않아야 한다.
- 설정 값은 가능한 `@ConfigurationProperties`로 묶고 검증한다.

## 3. 패키지와 이름

- package-by-feature를 사용한다.
- `util`, `manager`, `helper`, `common`에 업무 코드를 몰아넣지 않는다.
- 클래스 이름은 책임을 드러낸다.
- `Service` 하나에 모든 명령과 조회를 계속 추가하지 않는다.
- 인터페이스는 대체 가능성 또는 경계가 있을 때 만든다.
- 단순함을 해치면서 패턴을 적용하지 않는다.

## 4. 애플리케이션 서비스

Application Service는 다음을 조정한다.

- 트랜잭션
- 인증 사용자와 소유권
- Repository 호출
- 도메인 메서드 호출
- 이벤트 발행
- 응답 DTO 생성

하나의 유스케이스가 너무 많은 모듈을 직접 호출하면
모듈 경계 또는 책임을 다시 검토한다.

## 5. 트랜잭션

- 쓰기 유스케이스는 명시적으로 트랜잭션을 사용한다.
- 조회는 필요하면 read-only를 사용한다.
- Controller에서 트랜잭션을 열지 않는다.
- 외부 네트워크 호출을 긴 DB 트랜잭션 안에서 수행하지 않는다.
- 이벤트 처리 실패 정책을 명확히 한다.

## 6. JPA

- LAZY 로딩을 기본으로 고려한다.
- 화면 요구 때문에 무분별하게 EAGER로 바꾸지 않는다.
- N+1은 실제 조회 쿼리를 확인해 해결한다.
- 모든 관계를 양방향으로 만들지 않는다.
- Entity equality는 식별자 생명주기를 고려한다.
- setter 공개보다 의미 있는 도메인 메서드를 사용한다.
- 컬렉션 전체를 외부에 직접 노출하지 않는다.

## 7. DB 마이그레이션

경로 예시:

```text
src/main/resources/db/migration
V001__create_identity_tables.sql
V002__create_residence_tables.sql
V003__create_issue_tables.sql
```

규칙:

- 적용된 마이그레이션 파일을 수정하지 않는다.
- 새 변경은 새 버전으로 추가한다.
- destructive migration은 백업·전환·롤백 전략을 문서화한다.
- 인덱스는 실제 조회 패턴과 제약 조건을 기준으로 추가한다.
- 스키마 자동 생성은 로컬 실험 외에는 사용하지 않는다.
- 테스트에서 빈 DB부터 전체 마이그레이션을 검증한다.

## 8. 예외

- 도메인 예외는 의미 있는 이름을 쓴다.
- Repository의 기술 예외를 Controller까지 그대로 흘리지 않는다.
- `Exception`을 광범위하게 catch하고 무시하지 않는다.
- 사용자 메시지와 개발자 로그 메시지를 분리한다.
- 예외에 민감정보를 넣지 않는다.

## 9. 로깅

구조적이고 검색 가능한 로그를 남긴다.

권장 필드:

```text
event
traceId
userId
resourceType
resourceId
result
```

전체 요청 본문, 세션, 토큰, 메시지 본문은 기본적으로 로깅하지 않는다.

## 10. 의존성

새 의존성 추가 전 기록:

- 해결하려는 문제
- 표준 라이브러리 또는 기존 의존성으로 가능한지
- 유지보수 상태
- 보안 영향
- 번들 크기와 운영 영향
- 제거 가능성

에이전트가 제안한 라이브러리는 실제 존재 여부와 공식 문서를 확인한다.

## 11. 문서와 ADR

다음 변경은 ADR 대상이다.

- 인증 방식
- 모듈 경계
- DB 종류 또는 식별자 전략
- 외부 파일 저장소
- 이벤트 브로커
- LLM 공급자와 도구 실행 정책
- 마이크로서비스 분리
- 공개 API 버전 정책

작은 구현 세부 사항까지 ADR로 만들지 않는다.

## 12. Git 작업

- 한 변경은 한 목적을 가진다.
- 생성 파일과 비밀 파일을 커밋하지 않는다.
- 포맷 변경과 기능 변경을 무관하게 섞지 않는다.
- 커밋 또는 PR 설명에 변경 이유와 테스트 결과를 적는다.
- 대규모 자동 수정은 diff를 검토한다.
