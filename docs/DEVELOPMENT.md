# 개발 규칙

## 1. 환경

권장 기본:

- Java 21
- Gradle Wrapper
- PostgreSQL
- Docker Compose는 로컬 DB 재현에만 선택적으로 사용
- 환경별 Spring Profile

버전은 빌드와 Wrapper 파일에 고정한다.
개발자 PC에 설치된 전역 Gradle을 기준으로 삼지 않는다.

## 2. 설정

```text
application.yml
application-local.yml
application-test.yml
application-prod.yml
```

규칙:

- 공통 안전 설정만 기본 파일에 둔다.
- 비밀값은 환경 변수로 주입한다.
- 운영 profile을 기본값으로 자동 활성화하지 않는다.
- 테스트는 운영 DB나 외부 서비스에 연결되지 않아야 한다.
- 설정 값은 가능한 `@ConfigurationProperties`로 묶고 검증한다.

## 3. 패키지와 이름

- package-by-feature를 사용한다.
- `util`, `manager`, `helper`, `common`에 업무 코드를 몰아넣지 않는다.
- 클래스 이름은 책임을 드러낸다.
- `Service` 하나에 모든 명령과 조회를 계속 추가하지 않는다.
- 인터페이스는 대체 가능성 또는 경계가 있을 때 만든다.
- 단순함을 해치면서 패턴을 적용하지 않는다.

## 4. 애플리케이션 서비스

Application Service는 다음을 조정한다.

- 트랜잭션
- 인증 사용자와 소유권
- Repository 호출
- 도메인 메서드 호출
- 이벤트 발행
- 응답 DTO 생성

하나의 유스케이스가 너무 많은 모듈을 직접 호출하면
모듈 경계 또는 책임을 다시 검토한다.

## 5. 트랜잭션

- 쓰기 유스케이스는 명시적으로 트랜잭션을 사용한다.
- 조회는 필요하면 read-only를 사용한다.
- Controller에서 트랜잭션을 열지 않는다.
- 외부 네트워크 호출을 긴 DB 트랜잭션 안에서 수행하지 않는다.
- 이벤트 처리 실패 정책을 명확히 한다.

## 6. JPA

- LAZY 로딩을 기본으로 고려한다.
- 화면 요구 때문에 무분별하게 EAGER로 바꾸지 않는다.
- N+1은 실제 조회 쿼리를 확인해 해결한다.
- 모든 관계를 양방향으로 만들지 않는다.
- Entity equality는 식별자 생명주기를 고려한다.
- setter 공개보다 의미 있는 도메인 메서드를 사용한다.
- 컬렉션 전체를 외부에 직접 노출하지 않는다.

## 7. DB 마이그레이션

경로 예시:

```text
src/main/resources/db/migration
V001__create_identity_tables.sql
V002__create_residence_tables.sql
V003__create_issue_tables.sql
```

규칙:

- 적용된 마이그레이션 파일을 수정하지 않는다.
- 새 변경은 새 버전으로 추가한다.
- destructive migration은 백업·전환·롤백 전략을 문서화한다.
- 인덱스는 실제 조회 패턴과 제약 조건을 기준으로 추가한다.
- 스키마 자동 생성은 로컬 실험 외에는 사용하지 않는다.
- 테스트에서 빈 DB부터 전체 마이그레이션을 검증한다.

## 8. 예외

- 도메인 예외는 의미 있는 이름을 쓴다.
- Repository의 기술 예외를 Controller까지 그대로 흘리지 않는다.
- `Exception`을 광범위하게 catch하고 무시하지 않는다.
- 사용자 메시지와 개발자 로그 메시지를 분리한다.
- 예외에 민감정보를 넣지 않는다.

## 9. 로깅

구조적이고 검색 가능한 로그를 남긴다.

권장 필드:

```text
event
traceId
userId
resourceType
resourceId
result
```

전체 요청 본문, 세션, 토큰, 메시지 본문은 기본적으로 로깅하지 않는다.

## 10. 의존성

새 의존성 추가 전 기록:

- 해결하려는 문제
- 표준 라이브러리 또는 기존 의존성으로 가능한지
- 유지보수 상태
- 보안 영향
- 번들 크기와 운영 영향
- 제거 가능성

에이전트가 제안한 라이브러리는 실제 존재 여부와 공식 문서를 확인한다.

## 11. 문서와 ADR

다음 변경은 ADR 대상이다.

- 인증 방식
- 모듈 경계
- DB 종류 또는 식별자 전략
- 외부 파일 저장소
- 이벤트 브로커
- LLM 공급자와 도구 실행 정책
- 마이크로서비스 분리
- 공개 API 버전 정책

작은 구현 세부 사항까지 ADR로 만들지 않는다.

## 12. Git 작업

### 12.1 기본 원칙

- 한 커밋은 하나의 명확한 목적을 가진다. 기능 변경, 포맷 변경, 무관한 리팩터링을 섞지 않는다.
- 각 커밋은 가능한 한 독립적으로 빌드하고 검증할 수 있는 상태여야 한다.
- 사용자 요청 하나를 커밋 하나로 제한하지 않는다. 파일 수나 작업 시간이 아니라 기능적 완결성과 복구 가능성을 기준으로 커밋 시점을 판단한다.
- 비밀값, 개인정보, 로그, 빌드 산출물, IDE 개인 설정은 커밋하지 않는다.
- 자동 생성된 대규모 변경은 stage 전에 diff를 검토한다.
- 적용된 Flyway migration을 수정한 상태로 커밋하지 않는다.
- 사용자가 작업 전에 만든 변경을 에이전트의 커밋에 임의로 포함하거나 폐기하지 않는다.
- 상세 파일 변경 이력의 원본은 Git commit과 diff로 삼고 별도 누적 일지에 반복하지 않는다.

### 12.2 커밋 메시지

간단한 Conventional Commits 형식을 사용한다.

```text
<type>: <구체적인 변경 결과>
```

| 타입 | 용도 |
|---|---|
| `feat` | 사용자 기능 추가 또는 변경 |
| `fix` | 버그 수정 |
| `security` | 인증·인가·개인정보 등 보안 변경 |
| `test` | 테스트 추가 또는 수정 |
| `refactor` | 동작을 바꾸지 않는 구조 개선 |
| `docs` | 문서 변경 |
| `chore` | 빌드, 설정, 개발 도구, 저장소 관리 |
| `db` | DB 스키마 또는 마이그레이션 |

예시:

```text
feat: 생활 이슈 등록 기능 추가
fix: 다른 사용자의 이슈 조회 차단
security: Actuator 접근 정책 제한
test: 이슈 소유권 통합 테스트 추가
chore: PostgreSQL Testcontainers 환경 구성
docs: 프로젝트 진행 상태 갱신
db: identity 사용자 테이블 추가
```

- 제목은 변경 결과를 짧고 구체적으로 표현한다. `update`, `change`, `수정`처럼 의미가 불명확한 말만 제목으로 쓰지 않는다.
- 메시지는 실제 stage된 변경 전체를 정확히 설명한다.
- 기능과 직접 연결된 문서 갱신은 같은 커밋에 포함할 수 있다. 독립적인 문서 관리 작업은 `docs` 커밋으로 분리할 수 있다.
- 커밋 수를 늘리기 위한 인위적인 분할은 하지 않는다.

### 12.3 브랜치 사용 기준

초기 소규모 작업은 `main`에 직접 커밋할 수 있다. 개인 프로젝트이므로 모든 작은 작업에 브랜치나 Pull Request를 강제하지 않는다.

다음 작업은 별도 브랜치를 권장한다.

- 인증·인가 변경
- DB migration 추가 또는 변경
- 여러 모듈을 동시에 수정하는 기능
- 대규모 리팩터링
- 배포 또는 운영 설정
- 실패 시 되돌리기 어려운 작업
- 여러 자율 커밋이 예상되는 큰 기능

브랜치 이름은 목적을 드러낸다.

```text
feat/issue-create
feat/security-login
chore/postgres-testcontainers
fix/issue-ownership
refactor/task-boundary
```

에이전트는 안전한 작업 분리에 필요하면 일반 브랜치를 만들거나 전환할 수 있다. 먼저 현재 브랜치와 사용자 변경을 확인하고, 변경을 잃거나 섞을 위험이 없어야 하며, 완료 보고에 생성 또는 전환 사실을 남긴다.

### 12.4 자율 커밋과 체크포인트

에이전트는 변경이 독립적이고 복구 가능한 완성 지점에 도달하면 별도 확인 없이 관련 파일을 stage하고 local commit을 생성할 수 있다. 다음 조건을 모두 만족해야 한다.

- 하나의 기능, 기반 설정, 버그 수정, 테스트 작업 또는 문서 작업이 완결됐다.
- 해당 커밋만 checkout해도 프로젝트가 깨진 중간 상태가 아니다.
- 관련 테스트 또는 검증 명령이 성공했고 다음 작업과 분리해도 빌드와 동작이 일관된다.
- 한 줄의 커밋 메시지로 목적을 명확히 설명할 수 있다.
- 요청 범위 밖 변경이 없고 필요한 `PROJECT_STATUS.md`, `CHANGELOG.md`, ADR 갱신 여부를 확인했다.
- 비밀값, 개인정보, 로그, 빌드 산출물, IDE 개인 설정이 포함되지 않았다.
- 사용자 기존 변경과 에이전트 변경을 안전하게 구분할 수 있다.

하나의 요청이 여러 독립적인 완성 단계로 구성되면 여러 커밋으로 나눌 수 있다.

```text
chore: PostgreSQL 테스트 의존성 구성
test: Testcontainers 기반 컨텍스트 테스트 추가
docs: 영속성 기반 구축 상태 갱신
```

각 단계가 독립적으로 검증·복구 가능하고, 하나의 목적을 가지며, 중간 상태에서도 프로젝트가 유효할 때만 분리한다. 앞 커밋만 checkout하면 빌드가 실패하거나 뒤 변경 없이는 의미가 없다면 하나의 완결된 커밋으로 묶는다.

```text
chore: PostgreSQL Testcontainers 테스트 기반 구성
```

파일 하나, 오탈자, 중간 저장, 임시 정리, 채팅 수 또는 작업 시간만으로 커밋하지 않는다. 작은 요청은 하나의 커밋으로 끝낼 수 있고, 큰 요청은 리뷰·복구·이해가 쉬워지는 완성 체크포인트로만 나눈다. 마지막에 모든 변경을 무조건 한 커밋으로 합치거나 지나치게 작은 커밋을 만들지 않는다.

다음 상태에서는 자동 commit하지 않는다.

- 구현이 부분적으로만 끝났거나 임시 코드, 디버깅 출력, 의미 없는 TODO가 남았다.
- 테스트나 필수 검증이 실패했거나 환경 문제로 결과를 신뢰할 수 없다.
- migration과 이를 사용하는 코드가 분리되어 중간 상태가 깨진다.
- 사용자 기존 변경과 에이전트 변경을 안전하게 구분할 수 없다.
- 민감정보 또는 공개하면 안 되는 파일이 발견됐다.
- 변경 범위가 불명확하거나 요청을 벗어났고, 중요한 설계 결정에 사용자 판단이 남았다.
- 중단하거나 되돌릴 가능성이 높은 실험 단계다.

이 경우 완료된 범위, 남은 작업, 검증 실패 또는 미실행 이유, commit하지 않은 이유와 필요한 사용자 판단을 보고한다.

### 12.5 Stage 규칙

다음 순서로 현재 체크포인트에 직접 관련된 파일만 명시적으로 stage한다.

```text
git status
→ git diff
→ 관련 파일만 git add
→ git diff --cached
→ 테스트 결과 확인
→ git commit
```

- `git add .` 또는 `git add -A`를 기계적으로 사용하지 않는다.
- 다른 목적의 변경과 사용자 기존 변경은 stage에서 제외한다.
- 새 파일은 내용과 공개 적합성을, 삭제 파일은 의도된 삭제인지 확인한다.
- 비밀값이나 개인정보가 의심되면 stage와 commit을 중단한다.

### 12.6 커밋 전후 검증

Windows PowerShell의 기본 검증은 다음과 같다.

```powershell
git status
git diff
git diff --cached
.\gradlew.bat test
```

DB, Spring Security, 아키텍처 또는 빌드 설정을 변경했다면 다음까지 실행한다.

```powershell
.\gradlew.bat check
```

macOS 또는 Linux에서는 Gradle Wrapper 명령만 환경에 맞게 바꾼다.

```bash
./gradlew test
./gradlew check
```

커밋 전에 요청 밖 변경, 민감정보, 빌드 산출물과 로그, 테스트 범위, 문서 및 ADR 갱신 필요성, 기존 migration 수정 여부, 공개 포트폴리오 적합성을 확인한다. 검증하지 못한 변경은 자동 commit하지 않는 것이 기본이다. 문서 전용 변경처럼 테스트가 불필요하면 Markdown 링크와 diff를 검토해 대신 검증할 수 있다.

커밋 후에는 다음 명령으로 생성 여부, 포함 파일, 메시지, 남은 변경, 현재 브랜치와 테스트 유효성을 확인한다.

```powershell
git show --stat --oneline HEAD
git status
git log -1 --oneline
```

잘못된 커밋도 사용자 지시 없이 amend, reset, rebase 또는 삭제하지 않는다. 안전하면 새 수정 커밋으로 바로잡고, 이력 변경이 필요하면 사용자에게 보고한다.

### 12.7 Push 정책

push는 local commit과 별도 권한으로 취급한다.

- 조건을 만족하는 stage와 local commit은 에이전트가 자율적으로 수행할 수 있지만 `git push`는 항상 실행 전에 사용자 승인을 받는다.
- commit마다 묻지 않고, 사용자 요청 범위가 끝났거나 원격 백업에 적합한 안정 지점에서 전체 범위를 한 번만 제시한다.
- 사용자가 거절하거나 보류해도 local commit은 유지하며, 승인 전 추가 구현을 임의로 시작하지 않는다.
- 여러 커밋이 있으면 push할 전체 목록을 함께 보여준다.

승인 요청에는 다음을 포함한다.

```text
Push 대상
- Remote:
- Branch:
- 현재 원격 기준 이후의 commit 수:
- Push할 commit hash와 메시지:
- 실행한 테스트:
- 테스트 결과:
- 로컬에 남은 미커밋 변경:
- 공개 저장소에 포함될 민감정보 점검 결과:
```

승인 후에는 일반 push만 수행한다.

```powershell
git push
```

업스트림이 없다면 remote와 현재 브랜치를 확인한 뒤 설정할 수 있다.

```powershell
git push -u origin <branch>
```

push 후 `git status`, `git branch -vv`, `git log --oneline --decorate -5`로 결과와 원격 추적 상태를 확인해 보고한다.

### 12.8 사용자 통제와 금지 작업

다음 작업은 반드시 사용자 승인을 받는다.

- `git push`
- 최초 remote 추가 또는 기존 remote URL 변경
- GitHub 저장소 생성 또는 공개 범위 변경
- tag와 GitHub Release 생성
- 보호 브랜치 설정 변경
- Pull Request 생성 또는 병합
- Git 이력을 바꾸거나 파일을 폐기할 수 있는 작업

다음 작업은 사용자의 명시적인 요청과 검토 없이 수행하지 않는다.

```text
git push --force
git push --force-with-lease
git reset --hard
git clean -fd
git rebase
git commit --amend
Git 이력 재작성 또는 기존 commit 삭제
기존 remote 삭제 또는 교체
브랜치 강제 삭제
사용자 로컬 변경 폐기
GitHub 저장소 visibility 변경
인증정보를 remote URL에 포함
테스트 실패를 숨기고 commit 또는 push
```

공개된 비밀값은 새 커밋에서 삭제하는 것만으로 해결된 것으로 보지 않는다. 비밀값 자체를 출력하지 않고 폐기 또는 교체 필요, Git 이력 잔존 여부, 공개 노출 범위를 보고한다. 이력 정리가 필요하면 사용자 승인 후 별도 수행한다.

### 12.9 문서 기록과 커밋

- 기능, 보안, DB 스키마, 공개 API 또는 운영 방식이 바뀌면 `CHANGELOG.md` 갱신 여부를 검토한다.
- 프로젝트 단계, 완료 항목, 다음 작업 또는 알려진 위험이 바뀌면 `docs/PROJECT_STATUS.md`를 갱신한다.
- 중요한 기술 결정을 확정하거나 뒤집으면 ADR을 추가하거나 상태를 갱신한다.
- 직접 연결된 문서 갱신은 기능 커밋에 포함할 수 있고, 독립적인 관리 작업은 별도 `docs` 커밋으로 분리할 수 있다.
- 동작이 같은 리팩터링, 포맷·이름·테스트 정리는 Changelog에 기록하지 않는다.
- 파일별 수정 내역을 별도 누적 일지에 반복하지 않고 Git commit과 diff를 원본으로 삼는다.
