# ADR-0004: identity 로그인 및 식별자 전략을 정한다

- 상태: Accepted
- 날짜: 2026-08-05

## 맥락

초기 MVP에는 회원가입과 세션 기반 폼 로그인이 필요하다. 첫 identity Flyway
migration을 작성하기 전에 로그인 식별자의 형식과 유일성, 내부 PK와 외부 식별자의
역할을 정해야 한다.

초기에는 이메일 인증, 계정 복구, 공개 사용자 API가 범위에 없다. 반면 데이터 모델과
권한 검사는 처음부터 다중 사용자를 전제로 하며, 내부 DB PK를 HTTP 계약으로 고정하지
않아야 한다.

## 결정

### 로그인 식별자

- 초기 로그인 식별자는 이메일이 아닌 사용자명을 사용한다.
- 사용자명은 로그인 전용 식별자다. 사람에게 보여 줄 표시 이름이 필요해지면 별도
  필드와 정책으로 추가한다.
- 사용자명은 3자 이상 30자 이하로 제한한다.
- 첫 문자는 ASCII 영문자여야 한다.
- 나머지 문자는 ASCII 영문자, 숫자, 밑줄만 허용한다.
- 입력의 앞뒤 공백을 제거하고 `Locale.ROOT` 기준 소문자로 변환한 뒤 형식을 검증한다.
- 정규화 결과는 `^[a-z][a-z0-9_]{2,29}$` 형식을 만족해야 한다.
- 원래 입력한 대소문자 형태는 별도로 저장하지 않는다.
- 정규화된 사용자명에 데이터베이스 unique constraint를 적용한다.
- 탈퇴하거나 비활성화된 계정의 사용자명은 다른 계정이 재사용할 수 없다.

### 내부 및 외부 식별자

- 사용자의 내부 PK는 PostgreSQL `BIGINT`를 사용한다.
- 내부 PK는 인증 주체 식별과 다른 모듈의 `owner_id` 참조에만 사용하며 HTTP 요청이나
  응답의 공개 계약으로 노출하지 않는다.
- 초기에는 별도 외부 사용자 UUID를 만들지 않는다.
- 공개 사용자 API나 다른 사용자를 지정하는 기능이 실제로 필요해지면 외부 식별자와
  열거 방지 요구를 다시 검토한다.

### 비밀번호 저장

- 비밀번호는 Spring Security `PasswordEncoder`의 단방향 해시 결과만 저장한다.
- 저장 필드는 평문 비밀번호와 구분되는 `password_hash` 의미를 사용한다.
- 평문 비밀번호, 복호화 가능한 비밀번호, 비밀번호 힌트는 저장하지 않는다.
- 비밀번호 해시에는 unique constraint를 적용하지 않는다.
- 구체적인 해시 알고리즘은 migration에 고정하지 않고 보안 설정에서 관리한다.

## 대안

### 이메일을 로그인 식별자로 사용

사용자가 기억하기 쉽고 향후 복구 수단이 될 수 있지만, 현재 범위에 이메일 검증과
발송 기능이 없고 불필요한 개인정보 수집과 변경 정책이 필요해진다.

### 사용자명과 이메일 로그인을 모두 허용

로그인 조회, 충돌 처리, 계정 열거 방어가 복잡해지므로 초기 최소 범위에서 제외한다.

### UUID를 내부 PK로 사용

분산 생성에는 유리하지만 현재는 단일 애플리케이션과 데이터베이스를 사용하고 내부
PK를 외부에 노출하지 않으므로 추가 비용을 정당화할 요구가 없다.

### 원본 사용자명과 정규화 사용자명을 함께 저장

원본 표기를 유지할 수 있지만 로그인 식별자와 표시 이름의 역할이 섞인다. 초기에는
정규화된 로그인 식별자만 저장하고 표시 이름이 필요할 때 별도로 설계한다.

### 탈퇴 후 사용자명 재사용 허용

과거 기록의 주체 혼동, 사칭과 감사 추적 문제를 만들 수 있어 허용하지 않는다.

## 결과

장점:

- 이메일을 수집하지 않고 최소한의 로컬 폼 로그인을 구현할 수 있다.
- 대소문자와 공백 차이로 중복 계정이 생기지 않는다.
- 내부 PK와 향후 외부 식별자의 역할이 분리된다.
- 탈퇴 계정과 새 계정이 같은 사용자명으로 혼동되는 것을 방지한다.

비용과 위험:

- 국제화된 사용자명은 지원하지 않는다.
- 사용자는 가입 후 사용자명의 원래 대소문자 표기를 복원할 수 없다.
- 사용자명 재사용 금지를 유지하려면 계정 삭제 후에도 예약 정보를 보존해야 한다.
- 개인정보 삭제 요구와 사용자명 예약을 함께 만족하는 보존 방식을 별도로 결정해야 한다.

## 후속 조치

- 첫 identity migration과 persistence model에 이 결정을 반영한다.
- 애플리케이션 검증과 DB unique constraint를 함께 테스트한다.
- 중복 가입과 로그인 실패 응답에서 계정 존재 여부를 과도하게 노출하지 않는다.
- 계정 상태의 허용값과 초기값, 시간대 기본값은 구현 전에 별도로 확정한다.
- 계정 탈퇴 기능을 구현하기 전에 개인정보 삭제와 사용자명 예약을 함께 만족하는
  보존 정책을 정한다.
