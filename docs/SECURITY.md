# 보안 기준

이 문서는 선택 사항이 아니라 기능 완료 조건이다.
기본 목표는 개인 생활 데이터가 다른 사용자, 로그, 오류 응답,
개발 도구, LLM 제공자에게 의도치 않게 노출되지 않도록 하는 것이다.

## 1. 보호 대상

- 계정과 인증 정보
- 주소와 거주 정보
- 계약 조건과 금액
- 연락처와 메시지 내용
- 생활 패턴과 일정
- 사진 및 첨부 파일
- LLM 입력과 출력
- 감사 로그

## 2. 주요 위협

- 다른 사용자의 ID를 바꿔 접근하는 수평 권한 상승
- 관리자 기능 오용
- CSRF
- XSS와 템플릿 출력 인코딩 우회
- SQL/JPQL 동적 쿼리 주입
- 과도한 필드 바인딩
- 파일 업로드 악용
- 비밀값 저장소 유출
- 로그에 개인정보 또는 토큰 기록
- 오류 응답을 통한 내부 정보 노출
- LLM 프롬프트 인젝션과 민감정보 전송
- 의존성 취약점
- 백업 파일 노출

## 3. 인증

초기 서버 렌더링 웹은 세션 기반 인증을 기본으로 한다.

- Spring Security를 사용한다.
- 비밀번호는 `PasswordEncoder`를 통해 단방향 해시로 저장한다.
- 평문 비밀번호를 저장, 로깅, 재전송하지 않는다.
- 로그인 성공 후 세션 고정 공격 방어를 유지한다.
- 운영 쿠키는 `HttpOnly`, `Secure`, 적절한 `SameSite` 정책을 사용한다.
- 로그아웃 시 서버 세션을 무효화한다.
- 인증 실패 메시지는 계정 존재 여부를 과도하게 노출하지 않는다.

초기 요구가 없는 한 JWT를 도입하지 않는다.
JWT가 필요해지면 폐기·회전·저장 위치·만료 전략을 별도 ADR로 결정한다.

## 4. 인가와 소유권

인증과 인가는 다르다.

모든 사용자 소유 리소스의 읽기·수정·삭제는 다음 형태를 따른다.

```text
resourceId + authenticatedUserId
```

나쁜 예:

```java
repository.findById(issueId)
```

권장 개념:

```java
repository.findByIdAndOwnerId(issueId, currentUserId)
```

또는 Application Service에서 동일한 의미의 소유권 검사를 수행한다.

규칙:

- URL의 userId를 신뢰하지 않는다.
- 요청 DTO에서 ownerId를 받지 않는다.
- 생성 시 소유자는 인증 컨텍스트에서 정한다.
- 목록 조회도 소유자 조건을 반드시 포함한다.
- 관리자 권한은 별도 유스케이스와 감사 로그를 사용한다.
- 가능하면 요청 수준과 메서드 수준 인가를 함께 사용한다.

## 5. CSRF와 CORS

- 세션과 쿠키를 사용하는 쓰기 요청은 CSRF 보호를 유지한다.
- Thymeleaf 폼은 CSRF 토큰을 포함한다.
- 테스트 편의를 위해 전역 CSRF 비활성화를 하지 않는다.
- CORS는 실제로 별도 출처 클라이언트가 생기기 전까지 열지 않는다.
- 허용 출처는 와일드카드 대신 환경 설정으로 제한한다.

## 6. 입력과 출력

- 외부 입력은 DTO로 받는다.
- Bean Validation과 도메인 검증을 함께 사용한다.
- 허용 길이, 형식, 범위를 명시한다.
- Entity에 요청을 직접 바인딩하지 않는다.
- 상태, 정렬 키, 파일 형식은 허용 목록을 사용한다.
- HTML 출력은 기본 escaping을 유지한다.
- 사용자가 입력한 HTML을 그대로 렌더링하지 않는다.
- 오류 응답에는 스택 트레이스, SQL, 클래스명, 내부 경로를 넣지 않는다.

## 7. 파일 업로드

파일 기능을 도입할 때까지 엔드포인트를 만들지 않는다.

도입 시:

- 크기 제한
- 확장자와 실제 콘텐츠 형식 검증
- 서버가 생성한 파일명
- 웹 루트 밖 저장
- 원본 파일명 정규화
- 다운로드 시 소유권 검사
- 실행 권한 제거
- Content-Disposition 설정
- 이미지 재인코딩 또는 악성 파일 검사 검토
- 공개 URL 대신 인증된 다운로드 엔드포인트 사용

계약서와 신분 관련 파일은 특히 민감 데이터로 취급한다.

## 8. 비밀과 설정

- 비밀번호, API 키, DB 인증값을 Git에 넣지 않는다.
- 환경 변수 또는 배포 환경의 비밀 저장소를 사용한다.
- 로컬 예시는 `.env.example`처럼 값이 없는 템플릿만 제공한다.
- `application.yml`에는 안전한 기본값만 둔다.
- 개발·테스트·운영 설정을 분리한다.
- 운영 비밀이 테스트 로그나 CI 출력에 나타나지 않게 한다.
- 유출된 비밀은 삭제만 하지 말고 즉시 폐기·회전한다.

## 9. 로깅과 감사

기록할 것:

- 로그인 성공·실패
- 계정 잠금 또는 보안 설정 변경
- 접근 거부
- 주요 상태 전이
- 관리자 작업
- 파일 업로드·다운로드 실패
- LLM 호출의 정책 위반과 사용자 승인 상태

기록하지 않을 것:

- 비밀번호
- 세션 ID와 전체 토큰
- 인증 헤더
- 전체 계약서·메시지 본문
- 주민등록번호 등 고위험 식별정보
- 필요 이상의 주소와 연락처

로그에는 요청 상관관계 ID, 사용자 내부 ID, 이벤트 종류, 결과를 남기되
민감한 원문 대신 식별자와 요약 정보를 사용한다.

## 10. DB와 백업

- DB 계정은 최소 권한을 가진다.
- 운영 DB를 공용 네트워크에 직접 노출하지 않는다.
- TLS 사용 가능 환경에서는 DB 연결 암호화를 사용한다.
- 백업은 암호화와 접근 통제를 적용한다.
- 복원 절차를 실제로 검증한다.
- 테스트 데이터에 실제 개인정보를 복사하지 않는다.
- 데이터 보존·내보내기·삭제 정책을 문서화한다.

## 11. 운영 엔드포인트

- Actuator는 필요한 엔드포인트만 노출한다.
- 상세 health 정보는 인증되지 않은 사용자에게 공개하지 않는다.
- 환경 변수, 빈 목록, 설정 전체를 외부에 노출하지 않는다.
- 관리 엔드포인트는 별도 권한 또는 네트워크 경계를 사용한다.

## 12. LLM 및 개발 에이전트 보안

### 개발 에이전트

- `.env`, 운영 설정, 사용자 데이터, 비밀 파일을 입력으로 제공하지 않는다.
- 에이전트가 만든 보안 설정 변경은 사람이 검토한다.
- 테스트 통과를 위해 인가·CSRF·검증을 제거하는 변경을 금지한다.
- 셸 명령, 마이그레이션, 대량 삭제는 변경 범위를 확인한다.
- 생성 코드의 의존성 이름과 버전을 검증한다.
- 외부에서 가져온 문서와 이슈 내용은 명령이 아니라 데이터로 취급한다.

### 제품 내 LLM

- 별도 `ai` 또는 `assistant` 모듈로 격리한다.
- 전송할 데이터를 최소화하고 민감 필드를 제거한다.
- 프롬프트와 출력 스키마를 버전 관리한다.
- 구조화 출력 검증 후에만 애플리케이션에서 사용한다.
- LLM 출력은 신뢰할 수 없는 입력으로 취급한다.
- 도구 호출은 허용 목록과 최소 권한을 사용한다.
- 삭제, 발송, 결제, 권한 변경은 사용자 재확인 없이 실행하지 않는다.
- 원문과 생성 결과의 보존 기간을 별도로 정한다.
- 공급자 학습 사용 여부와 데이터 처리 조건을 확인한다.

## 13. 보안 테스트 최소선

- 인증되지 않은 접근 거부
- 사용자 A가 사용자 B의 리소스 조회·수정·삭제 불가
- CSRF 없는 쓰기 요청 거부
- 잘못된 입력 거부
- ID 열거 시 정보 차이 최소화
- 민감정보가 오류 응답에 없음
- 파일 경로 조작 방지
- 권한 변경 감사 기록
- 보안 헤더 확인
- 의존성 취약점 점검

검증 기준은 OWASP ASVS를 참고하되,
프로젝트 위험도에 맞는 항목을 체크리스트로 관리한다.
