# LLM 개발 에이전트 작업 지침

## 1. 목적

에이전트가 저장소 전체를 매번 읽지 않고도,
필요한 문서를 찾아 작은 범위로 안전하게 수정하도록 한다.

루트 `AGENTS.md`는 지도와 절대 규칙만 유지한다.
세부 정보는 문서 또는 가장 가까운 모듈의 `AGENTS.md`에 둔다.

## 2. 컨텍스트 로딩 순서

에이전트는 모든 작업에서 다음 순서를 따른다.

1. 루트 `AGENTS.md`
2. 작업 대상 파일까지의 경로에 있는 가장 가까운 `AGENTS.md`
3. 루트 문서 지도에서 관련 문서
4. 대상 모듈의 공개 API와 테스트
5. 실제로 변경할 파일

저장소 전체를 무작정 읽지 않는다.

## 3. 작업 유형별 필수 문서

### 새 기능

- `docs/PROJECT.md`
- `docs/ARCHITECTURE.md`
- `docs/DOMAIN.md`
- 대상 모듈 `AGENTS.md`
- `docs/TESTING.md`

### 인증·인가·개인정보·파일

- `docs/SECURITY.md`
- `docs/TESTING.md`
- 관련 ADR

### DB 변경

- `docs/DEVELOPMENT.md`의 마이그레이션 규칙
- 대상 모듈 데이터 모델
- 기존 migration
- 관련 persistence test

### API 변경

- `docs/API.md`
- 대상 Controller와 DTO
- 계약 테스트
- 공개 API라면 ADR

### 대규모 구조 변경

- `docs/ARCHITECTURE.md`
- `docs/decisions/`
- 새 ADR 초안

## 4. 에이전트가 먼저 확인할 것

구현 전 짧게 답할 수 있어야 한다.

- 어느 모듈의 책임인가?
- 변경되는 유스케이스는 무엇인가?
- 사용자는 누구이며 어떤 리소스를 소유하는가?
- 공개 계약이 바뀌는가?
- DB migration이 필요한가?
- 실패하거나 중복 실행되면 어떤 일이 생기는가?
- 보안 경계가 변하는가?
- 어떤 테스트가 실패해야 이 변경이 잘못됐음을 알 수 있는가?

답이 없으면 코드를 늘리기 전에 관련 문서 또는 ADR을 보완한다.

## 5. 구현 제약

에이전트는 다음을 하지 않는다.

- 새 프레임워크나 라이브러리를 근거 없이 추가
- 모든 계층에 인터페이스를 기계적으로 생성
- 요청 범위 밖 파일의 대량 포맷 변경
- 기존 migration 수정
- 테스트 삭제 또는 약화
- 보안 기능 비활성화
- Entity 직접 응답
- 사용자 ID를 요청 값으로 신뢰
- 예외를 삼키기
- 민감정보 로깅
- TODO만 남기고 완료 주장
- 실제로 실행하지 않은 테스트를 통과했다고 주장

## 6. 변경 크기

한 작업은 가능한 다음 단위로 제한한다.

```text
한 유스케이스
+ 필요한 도메인 변경
+ 필요한 migration
+ 테스트
+ 문서
```

여러 모듈을 동시에 크게 바꿔야 한다면
먼저 단계별 계획과 호환 전략을 작성한다.

## 7. 저장소 내 변경 기록

작업 완료 전에 다음을 확인한다.

- 현재 단계, 완료 항목, 진행 중인 작업, 다음 작업 또는 알려진 위험이
  바뀌었다면 `docs/PROJECT_STATUS.md`를 현재 상태로 갱신한다.
- 사용자 기능, 공개 API, 보안 정책, DB 스키마 또는 운영 방식이
  의미 있게 바뀌었다면 `CHANGELOG.md`의 `Unreleased`를 갱신한다.
- 중요한 기술 결정이 새로 확정되거나 기존 결정을 대체했다면
  ADR을 추가하거나 기존 ADR의 상태를 갱신한다.
- 단순 리팩터링, 오탈자, 포맷 변경, 테스트 이름 변경은
  `CHANGELOG.md`에 기록하지 않는다.
- 모든 파일 단위 수정 내용을 별도 일지에 반복하지 않는다.
  세부 diff와 커밋 단위 기록은 Git으로 관리한다.

## 8. Git 체크포인트 작업 흐름

상세 기준은 `docs/DEVELOPMENT.md`의 Git 작업 규칙을 따른다. 사용자 요청 하나가 반드시 커밋 하나를 뜻하지 않으며, 작업 중 다음 흐름을 반복한다.

```text
요청 분석
→ 구현 계획 수립
→ 변경 수행
→ 테스트와 검증
→ 의미 있는 체크포인트인지 판단
→ 관련 파일만 stage
→ staged diff 확인
→ local commit
→ 다음 작업 계속
→ 작업 범위 종료
→ 전체 commit 목록과 검증 결과 보고
→ 사용자에게 push 승인 요청
```

에이전트는 다음을 자동으로 수행할 수 있다.

- `git status`, `git diff`, `git diff --cached`, `git log`, `git show`, `git branch` 조회
- 현재 체크포인트와 직접 관련된 파일의 `git add`
- 조건을 만족하는 local `git commit`과 커밋 메시지 결정
- 안전한 작업 분리에 필요한 일반 브랜치 생성 또는 전환
- 커밋 후 상태 검증

브랜치를 만들거나 전환하기 전에는 현재 브랜치와 사용자 기존 변경을 확인해 변경을 잃거나 섞지 않는다. 부분 구현, 필수 검증 실패, 민감정보 의심, 사용자 변경과의 구분 불가 상태에서는 stage와 commit을 중단하고 이유를 보고한다.

다음은 반드시 사용자 승인을 받는다.

- `git push`
- 최초 remote 추가와 기존 remote URL 변경
- GitHub 저장소 생성 또는 공개 범위 변경
- tag와 GitHub Release 생성
- 보호 브랜치 설정 변경
- Pull Request 생성 또는 병합
- Git 이력을 바꾸거나 파일을 폐기할 수 있는 작업

다음은 사용자의 명시적 지시와 검토 없이 단독으로 수행하지 않는다.

- `git push --force`, `git push --force-with-lease`
- `git reset --hard`, `git clean`, `git rebase`, `git commit --amend`
- 기존 commit 삭제 또는 그 밖의 이력 재작성
- 사용자 로컬 변경 폐기
- remote 삭제 또는 덮어쓰기
- 브랜치 강제 삭제
- 저장소 visibility 변경
- 인증정보를 remote URL에 포함
- 테스트 실패를 숨기고 commit 또는 push

작업 범위가 끝나면 commit마다 묻지 않고 전체 local commit 목록과 검증 결과를 한 번에 보고한 뒤 push 승인을 요청한다. 승인 전에는 추가 구현을 임의로 시작하지 않는다.

## 9. 다음 작업 핸드오프

의미 있는 구현·수정 작업의 완료 답변에는 현재 저장소 상태를 기준으로 다음
권장 작업을 포함한다. 단순 질의응답, 코드 설명, 조사만 수행한 경우와 push만
수행한 경우에는 생략할 수 있다. 완료 답변을 보낸 뒤 다음 작업을 자동 실행하지
않고, 사용자가 선택해 실행할 수 있는 범위와 실행문을 넘긴다.

### 9.1 다음 작업 선정 순서

1. `docs/PROJECT_STATUS.md`의 현재 Phase, 완료 항목, 다음 작업과 알려진 위험을 확인한다.
2. 이번 변경으로 실제 완료된 항목을 반영한다.
3. 완료된 작업의 직접적인 후속 작업을 찾고 이미 끝난 작업은 제외한다.
4. 선행 조건이 충족된 후보만 남긴다.
5. 현재 Phase 목표에 가장 직접적으로 기여하는 작업을 우선한다.
6. 아키텍처, 도메인, 보안, 테스트 문서와 충돌하지 않는지 확인한다.
7. 독립적으로 구현하고 검증할 수 있는 크기로 제한한다.
8. 중요한 사용자 결정이 선행돼야 하는지 확인한다.

문서나 코드에서 근거를 확인할 수 없는 기능을 임의로 다음 작업으로 만들지 않는다.
완료 답변의 권장 작업과 갱신된 `docs/PROJECT_STATUS.md`의 첫 번째 다음 작업은
서로 일치해야 한다.

적절한 다음 작업은 하나의 개발 기반 구성, migration과 대응 persistence 모델,
하나의 use case와 테스트, 하나의 보안 정책과 검증 또는 하나의 명확한 기술 부채
수준이다. import·오탈자 한 건처럼 지나치게 작거나 인증·issue·task·dashboard를
동시에 구현하는 것처럼 지나치게 큰 범위는 피한다.

### 9.2 권장 다음 작업 출력

```text
### 권장 다음 작업

- 작업명:
- 목표:
- 선정 근거:
- 선행 조건:
- 예상 변경 범위:
- 제외 범위:
- 검증 방법:
- 사용자 결정 필요 여부: 없음 또는 필요한 결정
```

## 10. Codex Goal 사용 적합성 판단

권장 다음 작업마다 Goal 사용 적합성을 다음 중 하나로 표시한다.

- `권장`: 현재 상태에서 Goal로 시작할 수 있다.
- `비권장`: 명확한 소규모 작업이므로 일반 프롬프트가 적합하다.
- `결정 후 권장`: 중요한 사용자 결정이 완료되면 Goal에 적합하다.

Goal을 무조건 추천하거나 열린 백로그 전체와 무기한 개선 작업에 사용하지 않는다.

### 10.1 Goal 권장 기준

다음 특성을 여러 개 만족하면 `권장`을 고려한다.

- 일반 프롬프트 한 번보다 큰 다단계 작업이며 하나의 지속적인 최종 목표가 있다.
- 테스트, 명령 결과, benchmark 또는 산출물로 완료를 입증할 수 있다.
- 중간 결과에 따라 다음 시도가 달라지거나 반복적인 구현·검증이 필요하다.
- 여러 checkpoint를 거치고 사용자의 반복적인 계속 지시가 예상된다.
- 완료와 차단 상태를 구체적으로 정의할 수 있다.
- 현재 Phase 또는 하나의 기능 MVP처럼 서로 관련된 작업 묶음이다.

framework·dependency migration, 여러 계층의 기능 MVP, 대규모 리팩터링, 반복
재현이 필요한 버그 조사, 성능 benchmark, 다단계 보안 강화가 대표적이다.

### 10.2 Goal 비권장 기준

다음은 일반 프롬프트를 사용한다.

- 파일 하나의 단순 수정이나 한 번에 끝나는 설정 추가
- 원인과 수정 범위가 명확한 단일 버그
- 문서 정리, 설명, 조사, Git push 또는 테스트 하나 추가
- 완료 경로와 변경 범위가 명확한 소규모 작업
- 중요한 사용자 결정이 먼저 필요한 작업
- 서로 관련 없는 백로그 묶음이나 종료 조건이 모호한 요청

사용자 결정이 먼저 필요한데 결정 후 작업이 여러 checkpoint를 요구하면 `결정 후
권장`, 결정 후에도 작은 작업이면 `비권장`으로 판단한다.

### 10.3 Goal 판단 출력

`표시 이름`은 사람이 완료 보고에서 Goal을 구분하기 위한 짧은 제목이다. Codex
`/goal` 명령에 별도의 이름 필드가 있다고 가정하지 않는다.

```text
### Goal 사용 판단

- 판단: 권장 | 비권장 | 결정 후 권장
- 표시 이름:
- 판단 근거:
- 원하는 최종 상태:
- 완료 조건:
- 검증 수단:
- 유지해야 할 제약:
- 허용 범위:
- 제외 범위:
- 반복 방식:
- 중단 조건:
```

## 11. 다음 작업 실행문

### 11.1 Goal 권장 시

사용자가 그대로 입력할 수 있는 완성된 `/goal` 명령을 제공한다. Goal 본문은 단순히
긴 작업 설명이 아니라 다음을 포함한 완료 계약이어야 한다.

1. 원하는 최종 결과
2. 완료를 입증하는 테스트 또는 산출물
3. 유지해야 할 제약
4. 먼저 읽어야 할 프로젝트 문서
5. 허용된 변경 범위
6. 변경하면 안 되는 범위
7. checkpoint별 검증 방식
8. 중간 결과에 따라 다음 행동을 고르는 기준
9. 추측하지 않고 중단해 보고할 조건
10. 독립적인 완료 지점의 local commit과 push 승인 정책

Markdown의 중첩 code fence가 깨지지 않도록 다음 형식을 사용한다.

````markdown
### 권장 Goal

표시 이름: <짧은 이름>

```text
/goal <현재 저장소 상태에 맞춘 완성된 목표 본문>
```
````

Goal mode를 사용할 수 없는 환경을 고려해 짧은 일반 실행 대안을 덧붙일 수 있지만,
같은 내용을 장황하게 중복하지 않는다.

### 11.2 Goal 비권장 시

억지로 `/goal` 명령을 만들지 않고, 이전 대화 없이도 실행 가능한 일반 프롬프트를
제공한다.

```text
### 다음 작업용 Codex 프롬프트

<사용자가 그대로 복사해 실행할 수 있는 완성된 일반 프롬프트>
```

일반 프롬프트에는 현재 확인된 프로젝트 상태, 작업 목표, 먼저 읽을 문서, 구현·제외
범위, 모듈 경계, 보안 요구사항, DB 또는 migration 요구사항, 테스트, 문서 갱신 기준,
Git 정책, 검증 명령과 완료 보고 형식을 포함한다. 저장소 문서를 그대로 복제하지
않고 필요한 문서를 먼저 읽도록 지시한 뒤 이번 작업의 핵심 제약만 요약한다.

다음 의미도 포함한다.

```text
이번 작업 범위를 벗어나는 후속 기능은 구현하지 마라.
완료 보고에는 그다음 권장 작업과 Goal 사용 적합성 판단을 다시 포함하라.
```

### 11.3 사용자 결정이 필요한 경우

인증 방식, 식별자 전략, 호환성을 깨는 API 변경, 도메인 경계, 개인정보 범위,
보존·삭제 정책, 운영 DB 버전, 외부 서비스, 유료 인프라, 배포 환경, 라이선스 또는
기존 migration 수정처럼 중요한 결정은 에이전트가 임의로 확정하지 않는다.

```text
### 다음 진행 전 결정 필요

- 결정할 내용:
- 현재 확인된 사실:
- 선택지:
  1. ...
  2. ...
- 각 선택지의 영향:
- 권장안:
- 권장 이유:
```

필요하면 사용자 선택 placeholder가 포함된 일반 프롬프트나 Goal 초안을 제공한다.

## 12. 간단한 후속 명령

같은 대화에서 사용자가 `권장한 방식으로 다음 작업 진행해.`라고 입력하면 직전
완료 답변의 실행 권장 방식을 따른다.

- Goal이 권장됐다면 직전에 작성한 Goal 계약을 기준으로 Goal mode 실행을 준비한다.
- 일반 프롬프트가 권장됐다면 직전에 정의한 일반 작업 범위를 수행한다.
- 사용자 결정이 필요하면 구현하지 않고 결정을 다시 명확히 요청한다.

실행 전에는 현재 branch, Git status, 직전 이후 commit, 사용자 변경,
`PROJECT_STATUS.md`, 관련 문서와 권장 작업의 유효성을 다시 확인한다. 저장소 상태가
바뀌었다면 직전 실행문을 그대로 적용하지 않고 범위를 조정한 이유를 설명한다.

## 13. 완료 답변 형식

의미 있는 구현·수정 작업은 다음 순서로 보고한다. 해당 사항이 없으면 `없음` 또는
갱신하지 않은 이유를 적고, 실제로 실행하지 않은 명령을 성공했다고 쓰지 않는다.

```text
### 구현 결과

### 변경한 파일

### 설계 이유

### 보안 영향

### DB 및 migration 영향

### 테스트와 검증

### Git 작업

- 현재 브랜치:
- 생성한 commit 수:
- commit hash와 메시지:
- commit별 주요 변경:
- 원격에 반영되지 않은 commit:
- 남아 있는 미커밋 변경:

### 문서 기록

- PROJECT_STATUS.md:
- CHANGELOG.md:
- ADR:

### 남은 문제와 위험

### 권장 다음 작업

### Goal 사용 판단

### 권장 Goal
또는
### 다음 작업용 Codex 프롬프트

### Push 대상 및 승인 요청
```

자율 commit을 만들지 않았다면 `Git 작업`에 commit하지 않은 이유를 적는다. local
commit이 있으면 push 승인 요청에 remote, branch, 원격 기준 이후 commit 수, push할
전체 hash와 메시지, 테스트 결과, 남은 미커밋 변경과 민감정보 점검 결과를 포함한다.
commit마다 묻지 않고 작업 범위가 끝났을 때 한 번만 묻는다. Goal 또는 일반
프롬프트는 push 질문보다 앞에 두며, push 질문은 항상 완료 답변의 마지막에 둔다.

명령을 실행하지 못했다면 그 사실과 이유를 명시한다.

## 14. 로컬 AGENTS.md를 추가할 시점

다음 중 하나가 있을 때만 모듈 안에 추가한다.

- 모듈 고유 불변식
- 특별한 상태 전이
- 외부 시스템 계약
- 일반 규칙과 다른 테스트 명령
- 민감 데이터 처리 규칙
- 특정 파일을 변경할 때 반드시 함께 수정할 대상

단순히 루트 문서를 반복하기 위해 만들지 않는다.

## 15. 로컬 지침 예시

```text
src/main/java/com/example/livinghub/issue/AGENTS.md
```

이 파일에는 Issue 모듈의 상태 전이, 공개 API, 이벤트,
필수 테스트 위치만 적는다. 전체 프로젝트 규칙은 반복하지 않는다.

## 16. 문서 부패 방지

- 구현과 문서가 다르면 같은 변경에서 수정한다.
- 삭제된 경로를 문서 지도에 남기지 않는다.
- 루트 AGENTS가 길어지면 상세 규칙을 문서로 이동한다.
- 중복된 규칙은 한곳만 원본으로 두고 링크한다.
- 정기적으로 깨진 링크와 오래된 ADR 상태를 확인한다.
